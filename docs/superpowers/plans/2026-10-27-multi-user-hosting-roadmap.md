# 多用户应用托管实施路线

**目标：** 将现有单管理员 HTML 托管工具演进为支持个人、团队及自部署的开源前端应用托管平台。

**设计依据：** `docs/superpowers/specs/2026-10-27-multi-user-hosting-design.md`。

**架构：** 首版采用单机 Node.js、React、SQLite 和本地文件。管理端与应用域分离，每个应用使用独立 origin；不运行用户服务端代码。涉及跨域认证和不可信代码运行的设计须先完成浏览器安全验证。

**技术栈：** Node.js 22.13+、Express、React、Vite、SQLite、Node 内置测试框架。

## 当前实施状态（2026-10-29）

核心功能已经实现：邮箱注册、验证与重置；个人及团队工作空间、加入申请和角色授权；HTML/ZIP 上传、版本、回滚和配额；私有、公开及密码分享；独立应用域票据和逐资源授权；举报、停用、平台设置和保留策略；账号注销及中断恢复；旧页面离线迁移；脱敏安全日志、部署文档和 CI 配置。

已有验收证据：Linux ARM64 服务器上当前源码的 250 项测试全部通过；Windows 构建通过；独立 Chrome 在临时本机 HTTPS、独立应用域和模拟邮件下完成注册、团队审批、上传、版本回滚、分享、公开切换、注销、配额、举报和管理员流程。服务器公网获准端口到隔离 Nginx 健康接口的网络路径也已验证。

仍未具备正式公开体验条件：真实运营域名及通配解析、受信任 TLS 证书、真实 SMTP 投递、运营主体与隐私/投诉渠道、备案及适用治理流程、外部监控告警、生产备份恢复演练和 Docker 镜像验收均未完成。前述本机或合成数据测试不能替代这些生产验收，因此当前状态是“核心实现完成、生产上线未验收”，不是已可公开运营。

## 全局约束

- 官方体验版公开注册，面向中国大陆；自部署者可关闭注册并配置域名、邮件、额度和保留策略。
- 应用默认私有；支持团队管理、独立分享权限、版本更新与回滚。
- 应用支持 JavaScript、浏览器存储和外部 API；平台不提供用户服务端运行环境或业务数据库。
- 不同用户、工作空间和应用必须隔离；任何兼容性改动不得通过共用 origin 或暴露管理会话来实现。
- 生产环境要求 HTTPS 和应用通配符域名；现有数据迁移前备份，旧私有授权失效且不得自动公开。
- 每一阶段分别记录自动化测试、构建、真实浏览器检查和部署演练的结果；未执行的验收不得标为通过。
- 当前目录无 Git 元数据，无法使用提交作为检查点；恢复版本管理后再按阶段提交。

## 阶段 0：建立可验证的运行基础

**目标：** 固定当前基线，先确定不可信应用的运行和认证边界，避免后续返工。

- [ ] 对现有 API 测试、构建、登录和公开/私有应用资源链路记录基线；保留现有数据备份。
- [ ] 设计管理域、每应用子域与代理路由；明确保留域名、应用标识唯一性、删除后旧域名不能指向其他用户的规则。
- [ ] 制作隔离验证用应用：在两个应用 origin 中读写本地存储、发起外部请求、尝试读取对方资源和访问管理 API。验证 Cookie 域、跨域策略、服务工作线程、重定向、私有资源及分享撤销。
- [ ] 将验证结果形成独立技术决策：明确私有应用 HTML 与嵌套资源的授权方式、令牌存放位置、泄露与撤销处理，再选择可兼容前端应用的 CSP。若验证失败，保持当前隔离边界并修订方案。
- [ ] 建立版本化数据库迁移机制及可重复备份/恢复流程，在临时数据副本上验证中断恢复。

**涉及位置：** `server/app.js`、`server/page-access.js`、`server/config.js`、`server/database.js`、`test/api.test.js`、`README.md`；新增隔离验证材料及迁移模块的具体文件在阶段技术决策中确定。

**完成条件：** 现有功能可复现；真实浏览器证实两个应用之间和管理端之间的预期隔离；恢复演练有记录。认证方案没有证据前，不对外开放不可信应用。

## 阶段 1：账号与个人空间

**目标：** 用户能够安全注册、验证邮箱、登录并管理属于自己的应用。

- [ ] 增加用户、密码摘要、验证/重置令牌、会话和个人工作空间的数据模型与迁移；令牌单次使用、过期失效，密码不以明文保存。
- [ ] 配置邮件发送边界及注册开关；提供注册、邮箱验证、登录、退出、找回与重置密码，限制登录及邮件请求频率。邮件失败返回可理解的状态，不能标记为发送成功。
- [ ] 在页面查询与写入中绑定工作空间；用两个用户验证列表、详情、修改、替换、预览及删除均不能跨用户访问。
- [ ] 管理端增加注册、验证、登录及密码重置流程；对表单错误、过期链接和禁用注册提供恢复路径。
- [ ] 在复制的数据上实施单管理员数据迁移：显式选择接管账号和个人空间，保留原公开/私有状态，撤销旧私有授权；失败可从备份恢复。

**涉及位置：** `server/auth.js`、`server/repository.js`、`server/database.js`、`server/app.js`、`server/config.js`、`admin/src/api.js`、`admin/src/App.jsx`、`admin/src/components/`、`test/`。新增邮件、密码和令牌模块按独立职责拆分。

**完成条件：** 真实用户完成验证及密码找回；两用户越权测试通过；迁移和恢复可重复执行。此阶段可在受控环境试用，尚不能视为公开运营就绪。

## 阶段 2：团队与授权

**目标：** 团队通过申请和审批共同管理应用。

- [ ] 增加团队、成员、角色、申请及申请链接模型；实现链接创建、失效和重置，限制重复或高频申请。
- [ ] 实现所有者审批、拒绝、成员移除及角色调整；拒绝使团队失去最后一名所有者的变更。
- [ ] 建立统一授权检查：所有者管理空间和成员；编辑者创建、更新、回滚和管理分享；查看者只查看。覆盖每一个应用及成员 API。
- [ ] 增加团队切换、成员列表、申请提交和审批界面，说明当前角色与无权操作的原因。
- [ ] 验证申请前、待审批、批准、拒绝、移除和角色变更后的即时访问行为；验证个人空间与多个团队之间的数据隔离。

**涉及位置：** `server/database.js`、`server/repository.js`、`server/app.js`、`admin/src/App.jsx`、`admin/src/api.js`、`admin/src/components/`、`test/`。团队授权应抽离为单独模块，供所有路由复用。

**完成条件：** 两个工作空间和三个角色的授权矩阵通过 API 测试；真实浏览器完成申请、审批、发布与成员移除流程。

## 阶段 3：应用运行、分享和版本

**目标：** 在阶段 0 验证的隔离方案上，提供可运行前端应用和可控分享。

- [ ] 实现稳定的应用子域路由和安全的管理域隔离；检查通配符 DNS、HTTPS 与代理配置，错误配置时启动或部署检查给出明确提示。
- [ ] 支持 HTML/ZIP 上传、入口识别与多候选选择；继续拒绝路径穿越、符号链接、特殊文件和超出解压限制的内容。为用户说明根路径和 SPA 路由等实际支持范围。
- [ ] 实现默认私有访问、团队成员访问、公开访问、独立访问密码与撤销；令牌不写入应用管理凭证或不必要的日志。访问检查覆盖 HTML 和所有嵌套资源。
- [ ] 建立版本记录和有限历史保留，发布前完整校验，原子切换当前版本；支持回滚，并在中断后安全恢复或清理孤儿文件。
- [ ] 浏览器实测两个应用的脚本、本地存储、外部请求、跨应用隔离，及私有 ZIP 的 CSS/JS/嵌套资源；测试公开与私有切换、过期和撤销。

**涉及位置：** `server/app.js`、`server/archive.js`、`server/storage.js`、`server/page-access.js`、`server/tokens.js`、`server/repository.js`、`admin/src/components/PageDrawer.jsx`、`admin/src/api.js`、`test/`。

**完成条件：** 上传、访问、分享、更新、回滚的端到端流程可重复；身份变更、令牌撤销及故障注入下权限和当前版本保持正确。

## 阶段 4：公开实例治理与运维

**目标：** 满足官方公开体验版及自部署实例的基本运营需要。

- [ ] 配置上传大小、应用数量和存储额度；历史版本和进行中的上传计入限制，并检查并发上传不能绕过额度。
- [ ] 配置长期保留或按不活跃时间清理；界面展示规则，清理前邮件通知；通知失败记录并重试，不把失败当成已通知。
- [ ] 增加举报入口、管理员审核与停用应用，以及管理员操作审计；日志避免记录密码、会话及分享令牌。
- [ ] 提供部署配置、反向代理、邮件、HTTPS、备份恢复、升级回滚及故障排查文档；演练空实例部署和现有数据迁移。
- [ ] 增加服务健康检查、基本日志和异常告警接入说明；根据实际运营形式核查适用备案、隐私和内容治理要求。
- [ ] 对公开注册、上传、私有访问、举报、停用、备份恢复和移动端核心流程进行综合验收。

**涉及位置：** `server/config.js`、`server/database.js`、`server/repository.js`、`server/app.js`、`admin/src/`、`test/`、`README.md` 和新增部署文档。

**完成条件：** 管理员可配置并实际验证规则；在独立测试实例完成部署、恢复与治理流程；安全检查和已知限制形成上线记录。

## 执行方式和检查点

每个阶段开始前，将阶段范围拆成独立、可验证的任务，明确数据模型、接口、错误处理和测试，再进入实现。阶段 0 的浏览器验证结果决定阶段 3 的具体安全实现；不得提前假设当前 CSP 能直接满足可运行应用需求。每阶段结束先审查跨用户授权、数据一致性和迁移影响，再开始下一阶段。

路线图不直接给出精确工期：阶段 0 的隔离验证和现有应用兼容性结果会影响实现规模。付费、自定义域名、应用后端、公开团队目录及多人实时编辑不在首版范围。
