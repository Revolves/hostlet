# 旧页面离线迁移

此流程将旧单管理员页面逐个迁移到已验证账号的个人工作空间。迁移必须在单机停机状态下进行；它不会自动迁移任何页面。本功能已经过临时数据、进程中断和本机 HTTP 测试，尚未在真实部署或真实备份上演练。

## 开始前

1. 停止所有实例、后台任务和其他写入者。准备并验证完整离线备份：同一时刻的整个数据目录、SQLite 及其 WAL、所有应用文件、配置和必要密钥。备份与原目录必须相互独立。参考 [备份恢复步骤](superpowers/2026-10-27-database-migration-backup.md)。
2. 保留升级前的不可覆盖备份，按升级流程将数据库升级到当前版本并停止服务；再建立一份当前版本的完整离线备份。命令拒绝旧版数据库，不会替代升级前备份。源数据目录应保持旧版数据库中记录的绝对路径。
3. 确认目标账号已验证邮箱，拥有自己的个人工作空间；确认新应用域名、通配符 DNS 和 HTTPS 已正确配置。迁移后的地址使用新应用 ID，不再使用旧的 `/p/<slug>/` 地址。
4. 核对目标空间的应用数量和存储额度，并确保磁盘有足够空间容纳源文件、迁移副本及备份。每个页面最多迁移 20 个版本；超过上限、资源缺失、路径不安全或元数据不一致时会拒绝迁移，不会自动丢弃历史。

下面的路径和 ID 均为示例，替换成已核实的实际值。Windows 使用对应绝对路径。`list` 会显示已验证账号的邮箱及页面信息，仅供受信任的运维人员查看。

```sh
node server/migrate-legacy.js list --data-dir /absolute/data
node server/migrate-legacy.js inspect --data-dir /absolute/data --account-id ACCOUNT_ID --page-id PAGE_ID
```

预检展示所选页面的原访问状态、版本和大小；逐页检查。**原公开页面迁移后仍为公开**，服务重启后知道新地址的人即可访问；原私有页面仍为私有，不会继承旧管理员密码或旧分享授权。确认公开状态符合预期后，再对每个页面单独执行：

```sh
node server/migrate-legacy.js migrate --data-dir /absolute/data --account-id ACCOUNT_ID --page-id PAGE_ID --backup-dir /absolute/backup --confirm-backup
```

`--confirm-backup` 表示运维已按完整备份流程自行验证备份。命令还会检查备份数据库的完整性、版本、所选账号和页面元数据，以及所选页面每个版本文件的内容；它**不会验证其他页面、工作空间文件、配置或密钥是否完整**，不能代替完整备份和恢复演练。备份校验使用受限临时目录中的数据库副本，正常结束后清除该副本。

每次成功输出新应用 ID、目标空间和当前公开／私有状态，保留原有版本和创建时间。原页面的数据库记录在同一事务中移除，旧地址及私有授权随之失效；旧文件暂时留在原存储目录，不参与新应用的访问。迁移会将应用的最后更新时间设为迁移时间，避免新迁移应用立即触发不活跃清理。迁移完成后重启服务，使用目标账号验证版本、资源、公开状态和新地址，并重新创建需要的私有分享链接。

## 中断和恢复

迁移记录在复制文件前持久化。中途中断后，确认所有相关进程已停止；若实例占用标记残留，按[部署说明](deployment.md)处理。多用户服务启动时会先恢复未提交的迁移；也可离线执行：

```sh
node server/migrate-legacy.js recover --data-dir /absolute/data
```

恢复只清理有迁移记录且未被数据库引用的目标目录；遇到路径异常、符号链接或引用冲突时停止并保留现场。已提交的迁移不会被撤销，重复执行同一迁移会返回现有应用；如果该应用后来被删除，命令会报告目标不存在。极短的目录创建与记录写入之间若发生进程终止，可能留下空的未登记目录，不能自动判定并删除。不要直接删除未知目录。

如需回退已提交迁移，停止全部写入者，保存故障现场，并从同一完整备份恢复数据库、应用文件和配置；这会回退备份之后的其他更改。恢复旧数据库和旧密钥可能使尚未过期的旧私有链接重新有效，恢复前应评估并按部署流程轮换相关密钥。保留原始备份直至恢复和访问验证完成。
