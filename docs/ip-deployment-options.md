# 纯 IP 自部署：现状与方案

当前多用户托管依赖管理端与内容端分属不同注册域名，并为每个应用分配独立子域名。用户上传的页面可执行 JavaScript；仅使用同一个 IP 的不同路径或端口，不能沿用现有的域名和 Cookie 隔离模型。现有实现不会接受纯 IP 作为多用户应用域。

## 方案一：公网 IP + SSH 隧道测试

服务器只在回环地址启动独立测试容器，本机通过 SSH 隧道和测试域名访问。可以测试现有多用户流程，无需公网域名，也不会提供任何人可直接使用的纯 IP 地址。测试证书不受浏览器默认信任。

## 方案二：纯 IP 单管理员试用

采用现有单管理员模式，在独立容器和数据目录部署。此方案不是多用户平台，也不能提供当前多用户应用隔离保障。公网试用需要加密传输和严格访问限制，不应将其作为开放注册服务。

## 方案三：完整纯 IP 多用户支持

需要重新设计每个应用的浏览器隔离和访问授权，评估额外独立 IP、受限页面沙箱等技术选择及其对 JavaScript、存储、外部 API、分享和自部署复杂度的影响。单个 IP、无域名情况下，不能简单通过切换端口替代独立应用域的全部安全属性。该方案须经过权限、资源访问、跨应用攻击和浏览器兼容性验证后再部署。

建议先采用方案一完成服务器上的多用户功能演示，再单独确定纯 IP 多用户支持的隔离方案。服务器操作限定在 `/root/data/workspaces/html-server` 和已授权端口 30006–30008；不修改其他目录或已有容器，实际启动前检查端口占用。

## 纯 IP 多用户方案的进一步核验

现有内容服务使用每个应用的独立主机名、专用访问票据以及 `Secure`、`HttpOnly` 的 host-only Cookie；每个静态资源都重新检查授权。管理端和内容端还要求不同的可注册域。它依赖这些条件来隔离管理会话和不同应用，不能只改地址配置绕过校验。

单个公网 IP 下：不同端口虽然有不同的浏览器 origin，但 Cookie 按主机而非端口作用，且现有可用端口不足以为任意数量的应用各分配独立端口。多个应用放在同一内容 origin 的不同路径，则会共享该 origin 的浏览器存储与权限边界。仅添加路径前缀不能解决这些问题。

可以研究将每个页面放入强制沙箱，使其运行在不透明 origin：页面脚本仍可能运行，但通常无法使用原有的 `localStorage` 等同源存储；资源路径、外部接口、登录态、分享和下载也需逐项验证。它不自动继承现有私有资源逐项鉴权的保障。因此该方式最多是一个有明确兼容性限制的候选方案，尚非经过验证的完整实现。

2026-10-30 本机 Chrome 隔离实验使用 `Content-Security-Policy: sandbox allow-scripts` 和临时回环 HTTP 服务：脚本执行成功，向允许跨域的本机模拟 API 发起 `fetch` 成功；`localStorage`、`sessionStorage` 和 IndexedDB 均抛出 `SecurityError`。实验脚本为 `tmp/ip-sandbox-probe.cjs`，仅测试浏览器行为，不证明跨应用安全、生产 HTTPS、真实外部接口或产品整体可用。此结果不满足此前对浏览器存储的需求。

IP 上的 HTTPS 可以使用针对 IP 的证书或自签名证书，但证书是否受客户端信任取决于实际签发和客户端配置。HTTP 公网访问无法保护账号、分享链接和上传内容的传输。注册邮件中的链接也必须指向用户实际能够访问的地址。

无论采用何种候选设计，验收至少覆盖：同一浏览器中两个互不信任的应用不能读取或修改彼此数据和管理账户；私有 HTML、脚本、样式和图片均需授权，分享撤销与成员移除后立即生效；恶意页面不能绕过管理接口授权；多标签页及重启后状态正确；验证用户实际需要的 JavaScript、浏览器存储与外部 API 行为；以及公网 HTTPS、账号邮件和服务器重启后的数据持久性。未通过这些检查前，不将其作为开放注册的多用户服务。
