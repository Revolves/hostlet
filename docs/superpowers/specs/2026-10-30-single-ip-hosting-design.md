# 单 IP 自部署设计草案

状态：用户已接受可信团队及共享浏览器存储的取舍；已实现并部署自签名证书的受控试用，尚未完成正式生产验收。目标是在自有服务器使用单个 IP 和两个端口，让个人或可信团队无需 DNS、hosts 即可上传和分享静态前端。现有独立应用域模式继续作为不可信多租户的方案。

## 地址与访问

管理端 `https://IP:30006`，内容端 `https://IP:30007/p/<应用ID>/`。端口可由部署者配置；示例服务器的 30008 已有服务，不能使用。管理和内容使用不同 origin，应用资源通过内容路由获取。多用户登录、工作空间、版本与分享复用已有业务规则，但公开注册默认关闭，仅允许管理员控制的可信用户上传。公开注册不能与此模式同时开启；应用及其依赖脚本都必须可信。不同部署场景需自行限制网络访问与成员范围。

应用默认私有。成员或分享访客在管理端完成授权，再通过一次性票据交换获得短期内容访问会话；服务器对 HTML 和各静态资源逐次检查页面、权限、会话过期、分享撤销和停用状态。路径鉴权只是服务器访问控制，不能阻止一个已获授权且同源的恶意页面借访客浏览器发起对其他已授权页面的请求；不得向用户宣称跨应用访问或秘密隔离。使用审查后的独立实现与测试，不直接移除现有应用域校验。

## 本地存储与兼容性

内容端的页面可以使用原生 JavaScript、localStorage、sessionStorage 和 IndexedDB，但不同 `/p/<应用ID>/` 页面属于同一浏览器 origin，共享 localStorage、IndexedDB 等来源级空间。应用可以自行约定以应用 ID 为键前缀，减少意外冲突；该约定不提供安全隔离，不能防止其他页面读取、覆盖或清空数据。上传界面和部署说明必须显示这一事实。不能承诺每个应用有浏览器强制隔离的原生存储。

相对资源路径应工作；以 `/` 开头的资源引用、history API 路由和依赖站点根路径的前端构建需要配置应用基路径，不能保证无修改兼容。外部 API 受 API 本身的 CORS 和 HTTPS 混合内容规则约束。Service Worker 继续禁止，避免同源应用注册跨页面作用域的 worker。

## 管理端安全边界

不同端口不能隔离 Cookie。管理认证 Cookie 仍可能被浏览器发送至内容端；内容代理应尽量剥离管理 Cookie，后端不得记录 Cookie 或令牌。即使 HttpOnly 不允许脚本读取 Cookie，它仍可能随跨端口请求发送。必须对所有敏感读取和写入路径设计并测试严格的 Host、Origin、CSRF、防跨站导航、CORS、cookie 名称碰撞和权限校验；内容服务不可设置、覆盖或混淆管理凭据。不可仅凭 SameSite、Cookie Path、CORS 或仅针对写请求的 Origin 检查宣称安全。管理界面通过隔离 origin 和经测试的服务端防护保护，不承诺隔离同来源页面。

## 传输与运行

管理、内容都使用 HTTPS 和匹配 IP 的证书，维护者自行提供可信证书或在受控设备上配置信任；禁止将公开 HTTP 或跳过浏览器证书告警描述为安全生产方案。Let's Encrypt 已提供短期 IP 证书，但签发和自动续期有可达性验证要求；当前服务器不允许使用 80、443，不能假设可直接签发或续期。内网 IP 证书信任单独处理。邮件链接带实际管理端 IP 和端口；真实邮件发出前应确认目标地址与证书可用。

Docker 仅使用独立容器、专用网络和指定目录内的新数据目录；启动前检查端口、目录、证书及单实例锁，避免使用已有数据。不会修改现有容器、其他目录、系统服务或防火墙。保留现有域名模式，不自动迁移现有用户数据。

## 验收与发布门槛

1. 两个可信样例可通过 IP 打开，验证 HTML/ZIP、相对资源、JavaScript、原生存储及允许跨域的外部 API；同时实证不同页面可互相访问同源存储，并在界面明确提示。
2. 在新的隔离数据库验证注册关闭、登录、工作空间、上传、版本回滚、成员访问和分享；撤销或停用后每个资源请求被拒绝。
3. 通过独立浏览器模拟恶意内容页面对管理会话的读取、修改、跨端口请求、Cookie 覆盖、表单提交、重定向及缓存攻击；上述管理安全检查通过前不得发布供他人使用。
4. 验证根路径资源失败和用户可执行的基路径配置；测试多浏览器及重启数据持久性。
5. 区分本机自签名实验、服务器受控演练和真正可信 HTTPS 验收；生产备份恢复、滥用治理与监控单独验收。此模式不支持不可信多租户，不能因测试通过而宣传为应用间隔离。

## 待确定

用户已接受此模式不具备浏览器强制的应用间存储隔离。公网体验证书的签发和验证方式、现有页面根路径兼容性及管理端安全审计均尚未解决。
