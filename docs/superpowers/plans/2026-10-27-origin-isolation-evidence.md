# 应用隔离实验与技术边界

日期：2026-10-27。该记录用于后续实现决策，不代表多用户隔离已实现或通过安全验收。

## 现状基线

现有平台在同一内容 origin 下以路径区分应用；其 HTML CSP 使用 sandbox 且不允许 same-origin，因此浏览器本地存储无法满足新产品需求。现有私有资源授权使用路径中的签名令牌，管理员密码也用于私有页面，不适合公开多用户服务。现有安全策略保持不变，直到替代方案完成验证。

2026-10-27 使用本机回环运行原有测试：15 项通过；生产构建通过。沙箱内回环连接受限时，4 项 HTTP 测试报 fetch failed；在允许本机回环后全部通过。

## 本地浏览器实验

实验服务：`node test/isolation-lab/server.mjs`，仅监听 `127.0.0.1:43171`。以浏览器打开 `http://a.localhost:43171/` 和 `http://b.localhost:43171/`；这是本地 HTTP 实验，不等同于生产 HTTPS、反向代理或实际平台应用。

观察到两个 origin 各自写入并读出自己的 localStorage 和 host-only cookie；访问对方 iframe 的存储抛出 SecurityError，读取对方文档失败；读取无 CORS 授权的跨 origin 响应被浏览器阻止；同 origin 资源可以读取。两个方向均观察到相同结果。

实验中的 `/private` 是故意无认证的测试资源：浏览器阻止脚本读取响应不代表请求未发送，也不代表服务端有访问控制。实验未验证 TLS、真实域名、CSRF、域 Cookie 注入、服务工作线程、管理员会话、令牌撤销或私有 ZIP；这些均需后续验证。

## 推荐部署和安全约束

- 管理站点与不可信应用使用不同的可注册域名；应用使用独立子域。不同子域是不同 origin，但可能同属一个 site，不能单靠 SameSite 抵御跨站请求和 Cookie 投毒。
- 应用 ID 使用不可猜测的随机标识并且全局唯一。已删除标识保留墓碑，不重新分配给其他应用；反向代理拒绝未知 Host 和保留名称。域名分配不依赖用户可更改标题。
- 管理会话使用 Secure、HttpOnly、host-only Cookie，并优先使用 `__Host-` 前缀、Path=/ 和无 Domain 属性；管理接口还需严格验证 Origin/CSRF、角色权限和可信代理边界。不能将管理会话放到应用域或宽泛 Domain Cookie 中。
- 私有应用的每个 HTML 和静态资源请求都必须在服务端授权，不将 CORS 当作授权。优先研究应用专属、短期、可撤销的 host-only HttpOnly Cookie；登录或分享通过一次性短期票据交换，而不是在资源路径中传播长期授权。票据和 Cookie 绑定应用，禁止重放或跨应用使用。
- 访问密码、应用内容与身份提供者登录 UI 不应共享可由应用脚本控制的 origin。需要进一步设计独立可信授权域和跳转流程，并验证攻击者无法伪造授权页面、劫持或固定会话。不能假设独立子域自动满足这一点。
- 同一 origin 中的 service worker 能拦截该应用请求并持续存在。应用升级、权限撤销、删除与域名回收方案必须考虑已注册 worker 和缓存；首版应先定义清理及失效边界并验证，不能宣称服务端撤销能清除已下载内容。
- 应用可执行脚本及联网时，严禁依靠允许 same-origin 的 CSP sandbox 来隔离同一个 origin 内的授权页面。需要单独设计 CSP、下载内容类型、禁止缓存私有响应和默认安全头，同时验证外部 API 的 CORS 行为。

## 开放的验收工作

1. 在真实 HTTPS 和通配符 DNS/反向代理环境下验证 origin、site、Cookie、CSRF 和 Host 路由，包括恶意应用发起的请求与顶层导航。
2. 实现候选授权原型并验证私有 HTML、嵌套 CSS/JS、外部 API、票据一次性、撤销、过期、跨应用重放、重定向和日志泄露。
3. 验证 service worker、缓存和应用删除/回滚后的行为；明确已缓存内容无法远程收回的产品限制。
4. 保持现有系统 CSP，直到以上验证完成并审查安全设计；本实验不授予上线许可。
